# Protocol Scheduler Conformance

Reusable, capability-specific assertions for implementations of `protocol-scheduler`. Add this crate as a **development dependency** of a backend, then call its async test functions from that backend's integration tests while its executor and services are driven.

The file tests accept backend-created resources and paths. Each function requires only the capabilities it exercises. Socket assertions cover separate creation/binding/listening/connection/acceptance, scalar and prepared message I/O, short transfers, EOF, readiness, IPv4/IPv6 addresses, datagram boundaries, peek, truncation, empty datagrams, cancellation, and ownership. `socket::stream_pair` creates an isolated loopback fixture; individual I/O assertions also accept backend-created sockets. `SocketIoFixture` and `SocketIoGuard` expose a backend-controlled access boundary for deterministic completion/cancellation races and buffer retention after waiter abandonment, for scalar or vectored operations. Fixtures must release blocked access on destruction and enforce test deadlines. The blocking tests accept a `Blocking` implementation; deterministic queued-work tests additionally use a backend fixture that holds execution at a known boundary. No test assumes one runtime, task order, concrete descriptor, or prompt cancellation of a running syscall.

Tests panic on contract violations. The initial suite covers socket and message behavior, file contents and cursor semantics, ownership, pre-cancellation and lazy operations, positioned I/O, metadata, truncation, synchronization, compatible execution contexts, and blocking admission/ownership. Backend fixtures implement deterministic running-operation and retirement boundaries; scheduler shutdown, capacity/progress policy, and platform-specific behavior also need backend-specific tests. Unsupported capabilities must not be presented as passing tests.

The direct backend provides the first integration. Future adapters can run the same functions without depending on direct. Fixtures and assertions live here; backend-specific internal checks belong in backend crates.
