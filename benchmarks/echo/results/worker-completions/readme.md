# Native completion costs after the idle-search change

Fresh profiles of merged [#40](https://github.com/core-rs/core-scheduler/pull/40) reproduce the busy single-worker gap and identify the cost removed by deferred kernel task work. Across matched screens, the deferred policy improves borrowed echo throughput by 5.7–7.0% with 32 connections. It also raises single-connection P99 and sometimes reduces throughput substantially. None of the tested refinements establishes an improvement suitable for the default. This investigation changes no production Rust code.

The source base is `29d47375bf9a1b0239e9229335beb4d8beb0825b`. All comparisons use optimized release builds, locked dependencies, and a single frozen validating client. The [summary](summary.json) is generated by [summarize.py](summarize.py), which verifies complete matrices, unique samples, and the common client hash.

## Reproducing the gap

The [baseline](measurements/baseline/aiko.json) contains three shuffled repetitions per backend, with one worker and 32 connections. Rates are median validated echoes per second.

| Backend | 64 bytes | 4096 bytes |
| --- | ---: | ---: |
| Ordinary Tokio | 706,140 | 639,428 |
| Tokio retaining readiness until `WouldBlock` | 660,280 | 602,756 |
| Tokio adapter, borrowed | 653,156 | 580,754 |
| Native, borrowed | 637,815 | 567,034 |
| Native, owned completion-based receive | 641,675 | 582,915 |

Native borrowed throughput is 9.7–11.3% below ordinary Tokio in this run, and 3.4–5.9% below the conservative Tokio control. The conservative control changes Tokio's readiness API and read loop; it does not exactly match cancellation, task ownership, or resource bookkeeping. Its difference from ordinary Tokio is evidence about receive policy, rather than an isolated measurement of one syscall or a complete decomposition of the Native gap.

In these locked dependencies, ordinary Tokio clears readable readiness after a short successful read. Core retains it until `WouldBlock`, preserving the tested [TCP urgent-data behavior](../../readiness-performance.md#short-reads-and-tcp-urgent-data). All controls keep this distinction explicit. Neither Native path is substituted for the other: owned receives still submit io_uring `Recv`, while borrowed receives use synchronous nonblocking syscalls and persistent ring readiness.

## CPU and kernel work

The [separate CPU counter runs](measurements/cpu.json) use one worker, 32 connections, and 64-byte messages. Entries are median whole-server counts per measured echo across two runs, with zero warmup and three measured seconds. Startup and shutdown are included; counter-instrumented rates are not capacity results.

| Backend | User cycles | Kernel cycles | User instructions | Kernel instructions |
| --- | ---: | ---: | ---: | ---: |
| Native borrowed | 909 | 7,604 | 1,679 | 13,996 |
| Native deferred | 965 | 7,036 | 1,708 | 13,631 |
| Ordinary Tokio | 668 | 6,964 | 1,443 | 12,895 |
| Conservative Tokio | 822 | 7,270 | 1,717 | 13,669 |

Deferred processing removes about 568 kernel cycles per echo while adding 56 user cycles. It does more ring entries, not fewer. The [work counters](measurements/work.json) show Native's busy-case task-work runs falling from approximately 0.908 per echo to 0.071 deferred local-work runs per echo. Ring entries rise from 0.022 to 0.071 per echo; CQEs stay at approximately one per echo. With one connection, both policies retain one ring entry, one task-work run, and one CQE per echo.

The [syscall counters](measurements/stat/aiko.json) confirm two receive syscalls per borrowed Native or conservative Tokio echo, versus one for ordinary Tokio. Native owned receives issue no userspace payload-receive syscall. Futex calls, eventfd writes, and steady-state epoll registration are negligible here.

The [cycle profiles](measurements/perf/aiko.json) locate Native kernel samples in socket locking, task-work delivery, poll processing, and networking. Native borrowed CPU time is approximately 89% kernel time in the uninstrumented baseline. Symbol self-cost includes inlined callers and is not an isolated function cost; compressed self and callgraph reports remain beside the profile metadata. The profiles support investigating kernel completion handling and read policy, without attributing every remaining cycle to either mechanism.

## Ring-policy screen

The [ring screen](measurements/ring-screen/aiko.json) contains 60 uninstrumented samples. The deferred variant combines `SINGLE_ISSUER | DEFER_TASKRUN | TASKRUN_FLAG` setup with explicit zero-minimum `GETEVENTS` on productive submission turns. This measures that combined policy, rather than isolating setup flags. The setup and entry contracts are described in the [Linux setup manual](https://man7.org/linux/man-pages/man2/io_uring_setup.2.html) and [entry manual](https://man7.org/linux/man-pages/man2/io_uring_enter.2.html).

| Workers/connections/bytes | Current echoes/s | Deferred echoes/s | Change | Current P99 | Deferred P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1/32/64 | 636,372 | 673,763 | +5.88% | 54.751 µs | 51.871 µs |
| 1/32/4096 | 577,566 | 610,676 | +5.73% | 60.159 µs | 57.247 µs |
| 1/1/64 | 276,213 | 272,679 | −1.28% | 4.283 µs | 5.423 µs |
| 4/1/64 | 273,097 | 269,315 | −1.38% | 4.351 µs | 5.491 µs |

The low-load throughput difference varies considerably between screens. In the independent collection screen, deferred throughput is 8.0% lower at 1/1/64 and 4.2% lower at 4/1/64. Its corresponding P99 values remain higher. The busy-case gain repeats across screens; the low-load tradeoff from [#35](https://github.com/core-rs/core-scheduler/pull/35) remains after #40.

`NO_IOWAIT` is a separate wait-accounting and power-state control, not a pure userspace optimization. This diagnostic changes only indefinite waits; timed waits are untouched. The kernel supports the feature and accepts the flag in the retained setup traces. It makes deferred single-connection throughput approximately 7–8% worse than Current in this screen and does not improve the cooperative busy path. Host governor and idle policy were left as found.

## Completion collection and rejected refinements

The [collection screen](measurements/collect-screen/aiko.json) tests a bounded second CQ snapshot before returning to the executor. It runs on every `return_to_executor` path, including turns without submission. Submission receipts are consumed first; transient submit errors still return before the snapshot. It never waits again or chases newly generated work in the same turn.

With cooperative rings, borrowed throughput changes from −0.85% to +0.74% across the four cases, providing no established benefit. With deferred rings, busy throughput is 0.6–1.4% lower than deferred alone, and the low-load P99 regression remains. The [owned-read screen](measurements/owned-collect-screen/aiko.json) separately measures cooperative collection with actual completion-based receives: +1.18% at 1/32/64, +0.38% at 1/32/4096, −1.02% at 1/1/64, and −0.71% at 4/1/64. Those small mixed differences do not justify adding the snapshot to the default.

Two further screens reject narrower alternatives:

- [Zero-timeout batch requests](measurements/full-batch-screen/aiko.json) ask for CQ capacity completions with a zero timespec, treating `ETIME` as normal nonblocking completion. Busy borrowed throughput falls 14–27% below Current without the second snapshot and 13–14% with it. This deliberately different kernel wait path is not an improvement; these controls do not separately attribute its cost to timeout handling or the larger completion target.
- [Single-issuer and proactive-entry controls](measurements/probe-screen/aiko.json) add single-issuer setup alone, or explicitly enter when the SQ is empty and collect before returning. Single-issuer changes busy throughput by +0.27%, with mixed low-load results. Proactive cooperative entries are approximately flat. Proactive deferred entries retain a 5.38% busy gain but lose 7–10% in single-connection throughput. Additional speculative kernel entries do not resolve the tradeoff.

The [worker counters](measurements/batch-counts/aiko.json) explain why extra completion collection is not automatically better batching. At 32 connections, Current averages about 23–27 runnable executions per frozen ready batch; deferred averages about 12–13. These diagnostics include warmup and teardown, and their rates are not capacity evidence. `polls` counts runnable executions, including cleanup; `waits` counts idle driver attempts, which can return productively without sleeping. Neither is an absolute kernel-wait count or a count normalized to the measured request interval.

## Evidence and reproduction

The archive contains 291 uninstrumented capacity samples, eight worker-instrumented samples, 24 counter runs, four cycle profiles, and five setup traces. [measurements/manifest.json](measurements/manifest.json) records original and archived SHA-256 values. Samples are compacted onto individual JSON lines without changing parsed contents. Text profiles and setup traces use lossless gzip; full perf binary recordings, frozen executables, targets, and logs remain under `~/.cache/core-scheduler-single-worker-completions/` on Aiko.

Each screen preserves every repetition and its executable hashes. The [prototype patches](prototypes) are diagnostics against the recorded base; none is applied to production. Setup traces confirm accepted deferred/cooperative flags and actual `NO_IOWAIT` entries, rather than inferring support from optional setup calls. The scripts are Linux research tools for a disposable checkout, not portable package tooling:

- [build-prototypes.py](build-prototypes.py) builds the named ring-policy interventions and restores its source afterward.
- [build-diagnostic.py](build-diagnostic.py) adds worker batch counters, retaining its generated source patches.
- [measure.py](measure.py) uses the existing supervised profiler runner, freezes identities under the shared lock, rejects duplicate backend/binary identities, and randomizes cases and variants.
- [verify-setup.py](verify-setup.py) traces setup separately from performance measurements.
- [archive.py](archive.py) preserves decoded report contents and hashes while excluding perf binary recordings.
- [summarize.py](summarize.py) verifies every matrix and regenerates the summary.

The scripts use the recorded Aiko experiment paths. Prepare a clean disposable worktree at the base revision, copy these scripts into it, and create the experiment's `bin/`, `logs/`, and `results/` directories. Build the baseline with `CARGO_PROFILE_RELEASE_DEBUG=1 cargo build --release --locked -p core-scheduler-echo-benchmark`, then copy its executable into `bin/baseline`. Build the conservative Tokio control with the [existing control patch](../tokio-parity/diagnostics/tokio-conservative.patch), copy it into `bin/conservative`, and restore the benchmark source. Keep one `CARGO_TARGET_DIR` for the experiment and pass the frozen baseline as every client. `build-prototypes.py --variants NAME ...` selects the recorded interventions; it overwrites those variants' named binaries and patches, so finish builds before measuring and never overwrite frozen executables during a screen. `measure.py --variant NAME=BACKEND=BINARY --client BINARY --output NEW_DIRECTORY` runs the controls; add `--mode stat` or `--mode perf` for separately instrumented runs. The CPU and work counters use [wait-affinity.py](../idle-search/wait-affinity.py) with the same variant/client arguments, `--counters cpu` or `--counters work`, `--repeats 2`, and a new JSON output path. Pass `--cases 1:32:64` for CPU counters and `--cases 1:32:64 1:1:64` for work counters. That helper does not acquire the experiment lock itself; run it under `flock /tmp/core-scheduler-perf.lock`. Supervised profiling additionally requires noninteractive `sudo perf` and the existing tracepoints.

On Aiko, the Ryzen 9 9950X3D runs Linux 7.2.8 and Rust 1.99.0. Builds retain release optimization and debug information, with no LTO or target-CPU override. Server workers share CPUs 0–3 restricted to the worker count; the fixed four-worker client uses CPUs 4–7. These are separate physical cores in the same L3 group. Capacity samples use one second of warmup and three measured seconds; counters use zero warmup and three seconds; cycle profiles use one plus five seconds. All measurement phases and subsequent builds serialize on `/tmp/core-scheduler-perf.lock`. The initial frozen baseline and conservative binaries were built before measurements started. Background game/Wine processes were present mostly outside the benchmark CPU set, with broad affinity; their settings were not changed.

This is a closed-loop IPv4 loopback workload with one outstanding request per connection, reused 64 KiB buffers, `TCP_NODELAY`, complete partial writes, and validated payloads. Three repetitions per capacity cell do not establish sub-percent wins or production arrival-rate latency. Cross-screen baseline movement is substantial in some cases; compare candidates with their own screen's controls. Four-worker/many-connection throughput, other protocols, files, and timer latency are not remeasured because no candidate passes the focused throughput and low-load checks.

Keep cooperative rings as the default. The next useful kernel investigation is the deferred-mode wake-to-run and CQE-delivery delay under the normal idle policy, using probes light enough to preserve the uninstrumented ranking. Eliminating conservative read-policy cost needs an explicit semantic decision or a reliable drained-stream indication. More user-facing scheduler hooks are not supported by these results.
